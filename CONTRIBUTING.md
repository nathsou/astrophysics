# Learning experience

A chapter does not need a coding exercise. Choose the activity that reveals its central idea: a prediction, a calculation, an explanation of a counterexample, a small code edit, or a useful construction.

Before adding an exercise, state what the learner will discover by doing it. If the task only transcribes a displayed formula, formats a string, or repeats familiar plumbing, use a worked example or a question about the result. Supply scaffolding for mechanics outside the learning goal. A short activity should fit in roughly 5–15 minutes; label longer projects as optional extensions with prerequisites and a stopping point. Do not require every exercise to complete the conceptual path.

Long chapters need named sessions, explicit outcomes and a natural stopping point. Put the first working example before extended history. Introduce one primary proof or implementation before optional alternatives, with prerequisite links for advanced routes. Keep course-specific scientific and source-preservation conventions in their existing contributor guides.

Feedback must say what was established: visited, self-reviewed, answer checked, tests passed, or kernel checked. Historical completion does not verify edited code. Save drafts before a run, invalidate current results on edits, and bind asynchronous results to the submitted source. Exercise contracts must check the requested task, not just whether arbitrary code compiles.

Readers must be able to inspect explanations with a keyboard and a touch screen. Remember reading/detail preferences without forcing automatic scrolling. Test realistic workflows—edit after passing, reload a draft, move to the next section, and use the keyboard—in addition to builds and static links.
