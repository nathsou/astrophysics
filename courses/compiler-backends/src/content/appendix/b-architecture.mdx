## The classic 5-stage pipeline

The textbook RISC pipeline (Hennessy and Patterson) splits each instruction into five stages:
1. **IF** — fetch the instruction;
2. **ID** — decode it and read registers;
3. **EX** — execute or compute the address;
4. **MEM** — access memory;
5. **WB** — write the result back to the register file.

Ideally one instruction enters the pipeline every cycle and one leaves every cycle, even though each takes five cycles from start to finish.

**Hazards** break this ideal:

- **Data hazards**: an instruction needs a result that is not yet written back. **Forwarding** (bypassing) routes results from the EX or MEM stage straight to the next instruction’s inputs, removing most stalls. A load’s result is still only available after MEM, so an instruction that uses a load result immediately stalls for one cycle: the *load-use* hazard, which compilers schedule around.
- **Control hazards**: the pipeline fetches the next instructions before it knows where a branch goes. Guess wrong, and the work is discarded.
- **Structural hazards**: two instructions need the same unit in the same cycle, for example a single memory port.

## Superscalar and out-of-order execution

A **superscalar** core issues several instructions per cycle, provided they are independent and the functional units are free. That makes instruction order and dependence chains matter even more.

An **out-of-order** core (Tomasulo’s algorithm, 1967; universal in big cores since the mid-1990s) renames registers to remove false dependences. It holds a window of decoded instructions — hundreds, on modern cores — and executes each one when its operands are ready, retiring them in program order. It effectively performs dynamic list scheduling, with perfect knowledge of actual latencies, including cache misses. What it cannot do is:
- see past its window;
- fetch faster than its front end allows;
- avoid a misprediction’s penalty.

It also needs registers to rename *into*: its physical register file is much larger than the architectural one.

## Branch prediction

Branches are predicted, by pattern history and target buffers, many cycles before they execute. A modern predictor is right well over 95% of the time on typical code. A misprediction flushes everything fetched after the branch, costing 10–20 cycles on a deep pipeline.

Compilers help by:
- laying out code so the likely path falls through;
- converting unpredictable branches into selects (`cmov`, `csel`);
- unrolling loops to reduce branch count.

## The memory hierarchy

Approximate latencies on a modern core:

| level | latency | size |
|---|---|---|
| register | 0 cycles | 16–32 architectural, hundreds physical |
| L1 data cache | ~4–5 cycles | 32–64 KiB |
| L2 cache | ~12–15 cycles | 256 KiB – 2 MiB |
| L3 cache | ~40–50 cycles | tens of MiB, shared |
| DRAM | ~200–400 cycles | GiB |

This is why register allocation matters so much. A spilled value costs at least an L1 hit per reload — usually hidden by an out-of-order core, but not free: it occupies load ports and the store buffer, and it lengthens dependence chains. Store-to-load forwarding in hardware makes a reload right after a spill fairly cheap, but not zero.

## Why compilers still care

With out-of-order hardware, why schedule or care about latency at all? Because:
- many cores are **in-order** (efficiency cores, embedded RISC-V, Arm Cortex-A5x, GPUs);
- even big cores have finite windows, and long dependence chains serialise execution;
- code size affects the instruction cache.

A compiler that models the machine well can shorten critical paths and choose cheaper instructions; LLVM’s `llvm-mca` tool uses the compiler’s machine models to predict throughput.
