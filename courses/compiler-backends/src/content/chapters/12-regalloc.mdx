<p className="lede">
Register allocation decides, for every virtual register, which physical register holds it — or that it must live in memory. It matters more for performance than any other backend pass, and its classic formulation is one of the prettiest ideas in compilers: graph colouring.
</p>

## The interference graph

Two values **<Term k="interference">interfere</Term>** if one is live at a point where the other is defined. Interfering values cannot share a register, since writing one would destroy the other while it is still needed. Build a graph with a node per virtual register and an edge between each interfering pair: the **<Term k="interference-graph">interference graph</Term>**. A register assignment is then a **colouring** of this graph with *K* colours, where *K* is the number of allocatable registers. Adjacent nodes must get different colours.

The graph is built by walking each block backwards, maintaining the live set (Chapter 11):

```ts
for (const mi of reversed(block.instrs)) {
  if (isCopy(mi)) {                            // a move d <- s does not make d and s interfere:
    live.delete(src(mi));                      // they may share a register, and the copy disappears
    recordMove(mi);
  }
  for (const d of defs(mi)) for (const l of live) addEdge(d, l);
  for (const d of defs(mi)) live.delete(d);
  for (const u of uses(mi)) live.add(u);
}
```

The special case for **copies** is important. After `d ← s`, the two values hold the same bits, so they do not *need* different registers even if both stay live. Leaving that edge out makes it possible to assign them the same register and delete the copy. That is **<Term k="coalescing">coalescing</Term>**, and the SSA destruction of Chapter 10 relies on it.

**Physical registers** appear in the graph as <Term k="precolored">pre-coloured</Term> nodes. The ABI copies to `a0`, the implicit clobbers of a call and x86’s `rax`/`rdx` for `idiv` are all definitions of physical registers. They create edges to every value live at that point, and that is how the calling convention and fixed-register instructions constrain allocation with no special cases.

## Colouring is hard; Kempe’s trick is easy

Deciding whether a graph can be coloured with *K* colours is NP-complete for *K* ≥ 3. Chaitin showed that any graph can arise as the interference graph of some program, so register allocation inherits the hardness. Practical allocators use a heuristic whose core dates back to Alfred Kempe’s 1879 attempt to prove the four-colour theorem:

> If a node has fewer than *K* neighbours, remove it, colour the rest of the graph, and put it back. Its neighbours use at most *K − 1* colours, so a colour is always left for it.

This gives the classic two-phase algorithm:

1. **Simplify**: repeatedly remove a node of degree less than *K*, pushing it onto a stack. Removing a node lowers its neighbours’ degrees, which often makes more nodes removable.
2. **Select**: pop nodes one by one, re-inserting each and giving it a colour none of its already-coloured neighbours uses.

If simplification gets stuck — every remaining node has *K* or more neighbours — something must be **spilled**.

<p>Gregory Chaitin and colleagues at IBM Research built the first graph-colouring allocator for the PL.8 compiler and the 801 RISC machine: “Register allocation via coloring” (1981) and “Register allocation & spilling via graph coloring” (1982). Briggs, Cooper and Torczon made spilling <i>optimistic</i> (1989; TOPLAS 1994). George and Appel’s <i>Iterated Register Coalescing</i> (TOPLAS 1996) became the textbook algorithm, via Appel’s <i>Modern Compiler Implementation</i>.</p>
</Aside>

## Spilling, pessimistically and optimistically

When simplification is stuck, Chaitin’s allocator picks the node with the lowest **spill cost / degree** and spills it. The spill cost is the number of uses and definitions, weighted by 10^(loop depth), so values used in inner loops are expensive to spill. Dividing by degree prefers nodes whose removal helps the most neighbours. The spilled value is rewritten to live in memory (Chapter 14), and allocation starts over.

Briggs observed that this is too **pessimistic**. A node with *K* or more neighbours may still be colourable, because its neighbours might share colours. His **optimistic** variant pushes the stuck node onto the stack *as if* it were simplifiable, and only decides at select time. If a colour happens to be free when it is popped, no spill is needed at all. The classic example is a 4-cycle with *K* = 2: every node has degree 2, so Chaitin spills one, but it is 2-colourable.

## Coalescing without breaking colourability

Coalescing two nodes merges them into one node with the union of their edges. That can raise the degree enough to make the graph uncolourable, turning a free copy into an expensive spill. **Conservative** coalescing only merges when it provably cannot hurt:

- **Briggs’ test**: merge *a* and *b* if the merged node would have fewer than *K* neighbours of **significant degree** (degree ≥ *K*). The insignificant neighbours will all simplify away, leaving it with fewer than *K*, so it will simplify too.
- **George’s test**: merge *a* into *b* if every neighbour *t* of *a* either already interferes with *b* or has degree < *K*. It is especially useful when *b* is a pre-coloured register, whose degree is effectively infinite.

## Iterated register coalescing

George and Appel interleave coalescing with simplification, because simplifying lowers degrees and makes more conservative coalesces succeed. The algorithm keeps several worklists and repeats:

1. **simplify** a low-degree node that is not *move-related* (not an endpoint of a copy we still hope to coalesce);
2. otherwise **coalesce** a move that passes Briggs’ or George’s test, or mark it **constrained** if its endpoints interfere;
3. otherwise **freeze** a low-degree move-related node: give up on its moves and let it simplify;
4. otherwise choose a **potential spill** by cost/degree and push it optimistically;

then **select** colours, preferring for each node the colour of a node it has a move with, so that even non-coalesced copies often become `mv r, r` and vanish. Nodes that get no colour are **actual spills**. Spill code is inserted, and the whole process restarts on the rewritten program.

## What calls do to the graph

Look at the result for `@fib` in the pipeline below. The value `n` must survive the first recursive call, and the call defines every caller-saved register, so `n` interferes with all of them. The only colours left are the callee-saved `s` registers. The allocator puts `n` in `s2`, and the result of the first call — which must survive the second call — in `s1`. Frame lowering (Chapter 15) then saves and restores both in the prologue and epilogue. The calling convention’s split between caller- and callee-saved registers is being enforced by graph colouring.

## SSA-based register allocation

A deep result from the 2000s changes the picture. The interference graph of a program in **strict SSA** form is **chordal**: every cycle of four or more nodes has a chord. Chordal graphs can be coloured *optimally* in polynomial time, by assigning colours to values in dominance order, and their chromatic number equals the largest clique, which is MAXLIVE.

Hack, Grund and Goos (2006) built on this, and similar results came independently from Bouchez, Darte and Rastello, from Brisk et al., and from Pereira and Palsberg. The allocation problem splits in two:
- **spill** until MAXLIVE ≤ *K*, which is still hard but separate;
- then **colour** optimally in SSA and destroy SSA afterwards, which reduces coalescing to an easier problem.

This design is used in libFirm and has influenced JIT allocators.

<Aside kind="llvm">
<p>GCC’s allocator, IRA (Makarov, 2008), is a regional graph-colouring allocator: it colours loop regions bottom-up and pushes costs between regions. LLVM moved from linear scan to its “greedy” allocator in 2011. That allocator is not graph colouring: it assigns live ranges in priority order, evicting and <i>splitting</i> ranges when stuck (next chapter).</p>
</Aside>
